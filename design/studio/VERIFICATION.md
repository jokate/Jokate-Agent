# 사람이 할 확인

자동 테스트로는 볼 수 없어 사람이 직접 해 봐야 하는 확인을 작업마다 한 줄씩 적는다. 확인했으면 그 줄 끝에 날짜와 결과를 덧붙인다.

- [ ] S-7 프로젝트 맥락이 없는 폴더의 채팅 턴에도 studio MCP 가 붙는지 (ARCHITECTURE §9.5 의 알려진 제한) — 방법: 서버를 띄우고 (가) 미배치 직원(인사 등)의 1:1 방과 (나) 저장소 설정의 `project_context` 가 `false` 인 저장소에 배치된 직원의 1:1 방에 글을 하나씩 쓴다. 그 런의 활동 기록에 `project_context` 이벤트가 있고 그 `mcp` 에 `studio` 가 들어 있으면 붙은 것이다. 이벤트가 아예 없으면 프로젝트 맥락이 없어 studio 가 붙지 않은 것이다 — 답은 오지만 직원이 studio 도구를 쓰지 못한다. 붙지 않은 쪽이 있으면 어느 쪽인지 이 줄에 적는다 — 고칠 작업은 정해지지 않았다 (받을 작업 미정, ARCHITECTURE §9.5). — 2026-10-11 (가)만 확인, 붙었다: 미배치 시드 직원의 채팅 런 둘 다 `project_context` 이벤트가 있고 `mcp` 가 `["studio"]` 였다 (작업 폴더는 `runs/studio/employees/<직원 id>`). (나)는 보지 않았다.
- [ ] S-8 실제 서버를 죽였다 띄워 큐가 이어지는지 — 방법: 서버를 띄우고 같은 프로젝트의 backlog 작업 둘에 `POST /studio/tasks/{id}/start` 를 한다. 첫 작업의 런이 도는 중(`GET /studio/tasks/{id}` 의 첫째는 `status` 가 `working`, 둘째는 `queue_position` 이 1)에 서버 프로세스를 강제로 끝내고 다시 띄운다. 첫 작업의 `GET /studio/tasks/{id}/events` 끝에 `queued`(`detail.resume` 이 `true`)가 생기고 같은 `run_id` 의 런이 끊긴 단계부터 다시 돌며, 그 런이 멈춘 뒤 둘째 작업이 `working` 이 되어 새 런으로 돌면 통과다. 죽이기 전에 결정해 둔 결재가 있으면 다시 띄운 뒤 그 결재의 `delivery` 가 `delivered` 인지, 직원 상태가 담당 작업의 상태와 맞는지도 본다 (ARCHITECTURE §4.8 의 걸음 2 · 4).
- [ ] S-8 직원 설정과 이번만 덮어쓴 값이 실제 런의 모델 · 노력치로 들어가는지 — 방법: 서버를 띄우고 `GET /studio/models` 를 불러, 내주는 모델 · 노력치 가운데 담당 직원의 `employee.yaml` 의 `work` 값과 다른 것을 하나 고른다. 그 직원이 담당인 backlog 작업에 `POST /studio/tasks/{id}/start` 를 `{"stage_models": {"<단계 이름>": {"model": …, "effort": …}}}` 로 보내 한 단계만 덮어쓴다 (단계 이름은 그 작업이 도는 릴레이 파일의 것이다 — 릴레이가 `auto` 가 아닌 작업으로 한다). 런이 돌면 그 런의 활동 기록에서 단계마다 `stage_started` 이벤트의 `model` · `effort` 를 본다. 덮어쓴 단계는 보낸 값, 나머지 단계는 `employee.yaml` 의 `work` 값이면 통과다 — `work` 값이 상한(`model_cap` · `effort_cap`)을 넘으면 상한으로 낮춘 값이 맞고, Haiku 단계는 `effort` 가 `null` 로 나올 수 있다 (`pipeline.py` 1708–1709). 상한을 넘는 값으로 `start` 를 보내면 409 `precondition_failed` 와 `failed[]` 의 `model_over_cap`(노력치면 `effort_over_cap`)이 오는지도 본다 (ARCHITECTURE §9.5).
